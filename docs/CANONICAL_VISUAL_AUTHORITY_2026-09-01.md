# Research Drive — Canonical Visual Authority

**Authority ID:** `RD-CANONICAL-VISUAL-2026-09-01`

**Status:** FROZEN COMPOSITE PRODUCT / VISUAL AUTHORITY

**Date:** 2026-09-01

**Purpose:** End the ambiguity created by multiple historical `freeze` branches and later visual-hardening passes. This document defines which historical implementation/pixel families contribute to the next canonical Research Drive frontend.

This is **not** a claim that one historical commit contains the complete target. The final target is a deliberate composite: best proven topology + best proven visual treatment + current runtime/truth contracts. Any later implementation must converge to this authority; green tests are evidence of correctness, not permission to redefine it.

## 1. Binding governance rule

Order of authority:

1. Explicitly approved rendered pixels / state-family topology recorded here.
2. This canonical authority manifest.
3. Surface-specific historical freeze documents and implementation donors listed here.
4. Current runtime/truth contracts.
5. Browser and unit tests.
6. Incidental current CSS/JS layout.

A later CSS or test change may **not** redefine composition simply because it is loaded last or because CI is green.

Visual approval sequence:

`render actual repo -> inspect pixels -> approve -> then encode tests`

Never:

`change layout -> rewrite tests -> tests green -> call layout approved`

## 2. Shared shell / visual language

### Primary visual donor

- `5fc7bfb73097f6cd33d99f236b55c7386ceff00b` — **Premium research operating environment (#27)**

### Canonical grammar

- quiet paper / parchment research canvas;
- graphite navigation;
- hairline evidence surfaces rather than card walls;
- high evidence density where comparison is the task;
- contextual Detail | Ask rail;
- dark / ink reasoning treatment only when selection or deep work earns it;
- restrained cobalt / teal / green for consequential actions and state;
- no decorative AI theatre;
- no generic SaaS dashboard normalization across every surface.

### Rail rule

The rail is **state-aware**, not page-name-aware:

- no active object -> quiet orientation;
- simple selection -> interpretation + next valid action;
- deep workspace -> evidence / provenance / decision support;
- Ask -> same active context, conversational lens.

A global CSS rule must never blanket-hide the rail merely to reclaim width.

## 13. Freeze / change control

Changes that require explicit visual reapproval:

- changing shell column topology;
- adding/removing a persistent first-viewport section;
- replacing evidence rows with cards or vice versa;
- moving selection from contextual rail to centre takeover;
- hiding Detail/Ask in a selected/deep-work state;
- introducing a permanent workflow diagram or numbered process;
- adding KPI/dashboard strips to Home/Discover/Library;
- materially changing first-viewport density;
- changing primary Explore/History or Library/Synthesis workflow topology.

Changes normally allowed without reopening the authority:

- binding real data;
- replacing fixtures with current truthful values;
- accessibility corrections;
- responsive derivations preserving the same hierarchy;
- loading/empty/error states preserving topology;
- minor typography/spacing necessary to match approved pixels;
- current auth/provenance/readiness/runtime corrections.
